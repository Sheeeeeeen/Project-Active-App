# TRX Class Attendance — MVP Requirements

**Status:** Agreed for MVP  
**Platforms:** One Android and iOS app  
**Audience:** The person building this product

This document is the source of truth for the MVP. A requirement is in scope only if it is written here.

---

## 1. Product

Coaches run recurring TRX classes. Students attend those classes. The product records who was present at each session.

A student cannot mark themselves present with a button. Attendance is recorded only when the student first chooses which class they attended, then scans a QR code shown on the coach’s phone.

One app serves both roles. After sign-in, a coach sees coach screens and a student sees student screens.

## 2. Users

| Role | Who they are | What they can do |
| --- | --- | --- |
| Guest | No account | Browse public classes |
| Student | Registered client | Request a public class, accept an invite, scan attendance, view their own session history |
| Coach | Registered trainer | Create classes, invite students, approve requests, show the daily QR code, view attendance |

One account has one role. The role is set when the account is created and does not change. Registration does not offer a student/coach choice.

## 3. Terms

| Term | Meaning |
| --- | --- |
| Class | A repeating schedule created by one coach. The coach sets the days and the time. A day can have many classes, each with its own time. |
| Session | One date of that class. Sessions are numbered in date order: Session 1, Session 2, Session 3. The number stays on that date. |
| Roster | The students allowed to attend that class. |
| Public class | A class the coach has made visible to guests and students. |
| Private class | A class visible only to the coach and to students on its roster. Joining is by coach invite only. |
| Daily code | One QR code generated by a coach for the current date. It covers every class and every session that coach has that day. |

Attendance always belongs to one session, not to the class as a whole. Present at Session 1 does not mark Session 2 or Session 3.

## 4. Decisions

These choices are closed for the MVP.

| Decision | Choice |
| --- | --- |
| App structure | One app. Two experiences, selected by role. |
| Seeing classes | Public classes are visible with no account. |
| Creating an account | Required only when a student requests to join a class. A coach can also create an account from the registration screen. |
| Who can register as a coach | There is no role control on screen. On the registration screen, shaking the device switches that registration to a coach account. |
| How a student gets on a roster | The coach invites them, or the student requests and the coach approves. |
| How attendance is proved | The student scans a QR code on the coach’s phone. |
| Phone-to-phone NFC | Not in the MVP. An iPhone app cannot act as an NFC card for another phone outside a restricted European program. Android-to-Android would work, and any pair that includes an iPhone would fail. |
| Code lifetime | One code per coach per day, not one code per session. |
| Which class | Before the scan, a modal lists the classes scheduled that day. The student chooses the one they attended. The scan records that choice. The clock does not make that choice. |
| Offline | The coach can show the code with no internet. The student phone saves the scan immediately and uploads it when the phone is online. The saved time is the scan time. |

**Accepted limitation.** A photo of the daily code works for the rest of that day, during session times. A person who receives the photo can scan it in that window if they are on the roster. This is the cost of one code for the whole day.

## 5. MVP scope

In scope:

1. Class
2. Invite
3. Schedule
4. Attendance
5. Login

Out of scope:

- A second app for coaches or students
- Phone-to-phone NFC, or a physical NFC tag
- A student marking present with a button
- A student/coach switch, toggle, or role picker on registration
- Changing role on an existing account
- Payments, packages, or class capacity
- Notifications, announcements, or waitlists
- Messages between a student and a coach
- Editing attendance after it is recorded

## 6. Feature requirements

### 6.1 Class

The app opens on public classes. No account is required to view them. A button on this screen opens the registration screen. Coach registration is the shake on that screen.

**List.** Show every class a coach has marked public. Each item shows the class name, coach name, days, and time.

**Detail.** Opening a class shows that same information. Do not show the roster, attendance, or QR code.

**Request.**

- Guest: start student registration. After the account exists, send the request for this class.
- Signed-in student: send the request immediately.
- Coach: show no request action.

**Pending.** After the request is sent, the class shows Pending and Awaiting approval. Remove the request action so a second request is not sent. Keep that status until the coach approves or declines.

**Acceptance**

- A guest can open the list and a class detail with no account.
- A button on the public class screen opens registration.
- The detail does not show roster, attendance, or a QR code.
- A guest who requests a class completes student registration, and one request exists afterward.
- A signed-in student can send one request, and the class then shows Pending and Awaiting approval.
- A signed-in coach does not see a request action.
- Sending the request twice does not create two requests.

### 6.2 Invite

A student can be marked present only after they are on that class roster.

**Coach invite.** From a class, the coach searches an employee ID.

- One matching student account: the coach can send an invite to that class.
- No match: send nothing.
- The student sees a list of invites. Each invite can be accepted or declined.
- Accept adds the student to that class roster.

**Student request.** Requests from a public class are delivered to that class’s coach. More than one student can request the same class.

- The coach sees those requests in one list. Each request can be approved or declined.
- Approve adds that student to the class roster.
- Decline leaves that student off the roster.
- The public class pending status for that student ends when the coach approves or declines their request.

**Roster.** The coach can see the students on the class and can remove a student. A removed student is off that roster. The student sees the class as joined only after they accept an invite or the coach approves their request.

**Request again.** After the coach declines a request, or removes a student, that student can request the same class again. The class shows the request action, and the new request waits for the coach.

**Acceptance**

- Searching an unknown employee ID creates no invite.
- Searching a real employee ID lets the coach invite that student to the class they are managing.
- The student is on the roster only after accept or approve.
- Decline and removal leave the student off the roster.
- After a decline or removal, the student can send a new request for that class.
- A student who is not on the roster cannot gain a saved attendance record for that class.

### 6.3 Schedule

The coach creates the class that the Class list and Invite use.

**Create.** The coach sets:

- Class name
- Which days it repeats. This can be specific weekdays, or every day.
- Start time
- End time
- Public or private
- End date. When the coach sets one, that date is the last day the class stays open. When the coach sets none, the class stays open until the coach deletes or cancels it.

A coach can create many classes on the same day. Three or more is allowed. Each one has its own time. A public class appears in the Class list. A private class is joined only by coach invite.

**Sessions.** Saving the class creates every matching date from the save date through the class end date. The end date is included. A Monday and Wednesday class saved on 25 September 2026 with an end date of 31 October 2026 is open on every Monday and Wednesday from 28 September through 28 October 2026. A class with no end date has no year limit. Dates already past are not created. Deleting or cancelling the class is what stops an open class.

**Edit the series.** The coach can change the days, start time, or end time. The change applies to future sessions only. Past sessions remain as they were, including their attendance.

**Cancel.** The coach can cancel one date. That date can be today or a future date. The cancelled date does not accept attendance.

The other dates stay on the schedule. Cancelling this Monday does not cancel next Monday. Cancelling a future date does not remove the recurring days and time. The class keeps repeating.

**Acceptance**

- A coach can create a public class and a guest can see it.
- A coach can create a private class and a guest cannot see it.
- Saving a Monday and Wednesday class with an end date creates that class on every matching day from the save date through that end date.
- Saving a class with no end date keeps creating matching days past 31 December. The class stops when the coach deletes or cancels it.
- Saving an every-day class creates a date for every remaining day through the end date, or with no year limit when no end date is set.
- A coach can save three or more classes on the same day, each with its own time.
- Changing the series does not change a past session’s date, time, or attendance.
- Moving one session does not move the other sessions.
- Cancelling one date rejects a scan for that date only. The other dates of that class still accept attendance.

### 6.4 Attendance

The coach’s phone produces the proof of presence.

**Daily code.** The coach generates one QR code for the current date. The same code covers all of that coach’s classes and sessions that day. The coach can display it with no internet, including when the roster cannot be loaded. The screen shows that there is no internet connection. The code is valid for that date only, and only a code produced by the coach’s app is valid.

**Class choice.** The student opens attendance and a modal lists the classes scheduled that day, each with its time. The student chooses the one they attended. The scan does not start until they choose. Closing the modal stores nothing.

**Scan.** After the choice, the student scans the coach’s code. The QR proves they were with the coach that day. The attendance record uses the class they already chose. The clock is not used to decide it.

The date on the QR still separates days. This Monday’s 5:30 PM class and next Monday’s 5:30 PM class are separate attendance records. The student can scan again the same day and choose another class.

**Already recorded.** If the student scans for a class they already have a record for on that date, the app does not create a second record. It tells them they already have attendance for that class.

**Offline.** A student who was accepted onto the roster can scan with no internet. The phone keeps that scan and uploads it when a connection is available. The recorded time is the scan time, not the upload time. The screen shows that there is no internet connection.

**Rejected scans.** Store nothing when:

- The student is not on that class roster
- The code is for another date, or was not produced for that coach
- The student closes the modal without choosing a class, so the scanner never opens
- The session is cancelled

**Absent.** A student on the roster who does not scan for a class on that date is absent for that class. The day has to be over before they are marked absent. The phone’s timezone setting decides which date it is and when that day is over. A future date stays upcoming. Choosing one class marks that class present. Each other class on that date stays absent unless they scan again and choose it.

**Results.**

- For each date, the coach sees who is present, who is absent, and which class each present student chose.
- The student sees each date as upcoming, present, or absent.

**Acceptance**

- With no internet, the coach can still show the daily QR code, the roster may be unavailable, and the screen shows that there is no connection.
- A scan with no coach code does not mark the student present.
- The modal opens before the scanner and lists that day’s classes. Choosing one, then scanning, stores that class. The time of the scan does not change that result.
- Closing the modal without a choice does not open the scanner and stores nothing.
- The choice is stored on the phone, including when the phone is offline.
- After the phone is online, the coach sees the class the student chose.
- A roster student with no scan on a finished date is absent for the class they did not choose.
- A future date is not absent.
- A second scan for a class that already has a record shows that they already have attendance and does not create a second record.

### 6.5 Login

Public class remains available without an account. Login creates the account used by Invite and Attendance.

The registration screen has no control for choosing Student or Coach.

**Student registration.** This is the registration screen a guest opens. The person enters name, email, password, and employee ID. The employee ID is unique across accounts. Submitting creates a student account.

**Coach registration.** On that same registration screen, the guest shakes the device. The screen color and title change to show that this account will be a coach. They enter name, email, and password. There is no employee ID field. Submitting creates a coach account. Shaking again restores the student registration screen, including its color, title, and employee ID field.

Shaking does nothing on the registration screen opened from a public-class request. That path always creates a student account.

**From a public class.** A guest who requests a class completes student registration. After the account exists, the request for that class is sent.

**No email confirmation.** Submitting the form creates a usable account. The person does not have to open a link in their email.

**Sign in.** The registration screen includes sign in. Email and password open the screens for the account’s role. A signed-in student can request a public class immediately. A coach has no request action.

**Acceptance**

- The registration screen has no student/coach toggle, switch, or picker.
- The screen opens as student registration, with an employee ID field.
- Shaking the device changes the screen color and title, removes the employee ID field, and a submit creates a coach account.
- Shaking again restores student registration.
- Two students cannot register the same employee ID.
- A coach account has no employee ID.
- A guest who requests a class finishes as a student even if they shake the device during that registration, with one pending request on that class.
- The new account can sign in from the registration screen and send that request without confirming an email.
- After sign-in, a student does not see coach class setup, and a coach does not see the student scanner.

## 7. Main flows

### Student joins a public class

1. The guest opens a public class.
2. The guest chooses to request it and completes student registration.
3. The class shows Pending and Awaiting approval.
4. The coach approves.
5. The student sees the class as joined and can scan during its sessions.

### Coach creates an account

1. The guest opens the registration screen. It is student registration.
2. The guest shakes the device.
3. The screen color and title show coach registration.
4. The guest enters name, email, and password and submits.
5. Sign-in opens the coach screens.

### Coach invites a student

1. The coach opens a class and searches an employee ID.
2. The coach sends the invite.
3. The student opens their invite list and accepts.
4. The student is on that class roster.

### Student records attendance

1. The coach shows the daily QR code.
2. The student chooses one of that day’s classes in the modal, then scans the code.
3. The phone checks the roster and the date, and stores the class the student already chose.
4. A valid scan is saved on the phone and uploaded when possible.
5. The coach sees the student on that session. A later session stays unmarked until the student scans again inside that session.

## 8. Rules that must not drift

1. One account, one role. Registration does not show a role choice.
2. Coach registration is reached by shaking the device on the registration screen. The request-to-join registration path ignores that shake.
3. Employee ID is unique and belongs to a student.
4. Roster membership is per class.
5. A scan writes at most one attendance record per student per session.
6. The session number does not change when a future session is edited.
7. Series edits do not rewrite past sessions.
8. The class is chosen in the modal before the scan, from the classes scheduled that day. The scan time does not change that choice.
9. The daily code belongs to one coach and one date.
10. Offline storage happens on the student phone at scan time.

## 9. After the MVP

These are the next features. They are not part of the MVP build.

1. **Notifications.** The user is notified when a class is about to start, when a class date is cancelled, and when there is an announcement.
2. **Messages.** A student can send a message directly to the coach.

## 10. Open points

None. The decisions that were open are now in the feature rules above.
